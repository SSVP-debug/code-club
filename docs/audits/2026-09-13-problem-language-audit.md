## INFO findings — flagged for manual review, not auto-fixed

Per the audit's own instruction ("do not modify all 250 problems
automatically unless the correction is deterministic and demonstrably
safe... if ambiguous, flag for manual review"), these were **not**
auto-generated, because doing so would mean authoring new
problem-specific solution code or judgment calls a script can't safely
make:

- **27 problems are missing `starter/c.c`.** `c` is `enabled: true`
  (selectable in the Run/Submit language dropdown right now) but not in
  `REQUIRED_STARTER_LANGUAGE_KEYS`, so this isn't a schema violation — but
  it is a real, confirmed student-facing gap: `src/hooks/useProblemSolver.js`
  silently falls back to an empty string for a missing entry
  (`problem.starterCode?.[lang] ?? ""`), so a student selecting C on any
  of these 27 problems gets a **blank editor with no function signature**,
  no error, no indication anything is missing. Writing correct C starter
  code requires understanding each problem's specific signature and C's
  documented constraints for this codebase (no classes, no `string`, array
  arguments need a companion `<key>Size` — see
  `backend/utils/languageTypes/c.js`'s header comment), so this is
  genuinely not mechanical. **Recommendation: either backfill these 27
  (tracked, scoped work, similar to the completed TypeScript backfill), or
  set `c: enabled: false` until the backfill is done** — the second option
  is a one-line config change and immediately closes the gap for every
  student, at the cost of temporarily removing C as a selectable language.
  Full list of the 27 slugs is in the JSON report's `findingsByProblem`
  (filter for `"check": "starter-code"` and `"c" has no`).
- **0 problems** are missing TypeScript starter code — that backfill
  (referenced in `config/languages.js`'s TypeScript entry) is complete.
- **245 problems have fewer than 3 hidden test cases** (193 have exactly
  2, 52 have exactly 1). This is a coverage-strength judgment call, not a
  structural defect — a script can count hidden cases but can't safely
  invent new problem-specific edge cases the way it could for
  `sudoku-solver` (where "generate a puzzle with a unique verified
  solution" was a self-contained, verifiable operation; "generate a good
  edge case for `alien-dictionary`" is not). **Recommendation: treat this
  as a backlog, prioritized by how easy each problem is to game with a
  hardcoded/overfit solution given only 1-2 hidden cases** — the JSON
  report's `hidden-testcases.json` INFO entries give the exact count per
  problem to prioritize from.
- **2 problems** (`first-bad-version` and one other) triggered the
  `functionName`-appears-in-starter-code heuristic check as a false
  positive — this check is a plain substring search, not a parser, and
  both problems use a callback-wrapped signature convention where the
  literal function name legitimately doesn't appear as written. No action
  needed; flagged as a known heuristic limitation for whoever reviews the
  JSON report next.
